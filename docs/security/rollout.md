# Security rollout requirements

## Deployment gate

Deploy the backend/frontend together in a coordinated release. This work was implemented and tested locally with disposable MongoDB, generated PDF fixtures and a local OTP sink. Live OTP providers, storage ACLs, the export receiver and production cookie routing have not been changed or verified.

1. Set independent cryptographically random `JWT_SECRET` and `MEDIA_SIGNING_SECRET`, each at least 32 characters. Do not reuse database credentials or each other. Preserve existing provider encryption keys. Remove `SECURITY_OTP_SINK` entirely in production: any configured value is rejected.
2. Set exact `FRONTEND_URL` and `ALLOWED_ORIGINS`, including scheme and port where applicable. Use the frontend same-origin `/api` and `/uploads` rewrites. Build with an empty/same-origin `VITE_API_URL`; cross-site API cookies are intentionally incompatible with Strict cookies and the enforced CSP. Verify HTTPS and proxy preservation of `Set-Cookie`, `Cookie`, `Origin`, `X-CSRF-Token` and private/no-store responses before cutover. Confirm proxy-derived IPs are reliable; never trust arbitrary forwarded headers.
3. Configure live SMTP and NextSMS. Privileged accounts need an authorized existing email/phone destination. Test both channels with designated release-test accounts. Password alone cannot open a privileged workspace. OTP provider failure must not create a usable session. Initial-password setup sessions cannot access business resources.
4. Keep GridFS and Blob originals/private rendered assets inaccessible without the application. Blob storage must be private; cloud/CDN ACLs cannot be inferred from application tests. Legacy filesystem directories must be readable only by the app process. Only cover images are explicitly public. Do not publish the temporary download spool directory; local snapshots use mode 0600 and are removed after streaming. Monitor disk capacity and clean abandoned spool files after process crashes.
5. Configure `SECURITY_AUDIT_EXPORT_URL` with an HTTPS receiver and an independent `SECURITY_AUDIT_EXPORT_TOKEN`. Original delivery in production fails closed if export settings are missing. Delivery does not wait for a live receiver: the immutable database event is the durable outbox. Verify receiver write permissions with a synthetic event, outage/recovery, and event-ID deduplication before enabling production downloads.
6. Give the export identity append-only write rights to a separately administered logging destination. Deny read/delete/overwrite permission; use storage retention/immutability controls and a separate deletion administrator. Give the application MongoDB identity insert/find permissions on `securityevents`, not update/remove; provision indexes through a migration/operator identity. TTL expiry is performed by MongoDB. Other collections, including delivery leases, require their own normal app permissions. Mongoose hooks are defense in depth, not protection against database administrators.
7. Schedule authenticated `GET /api/internal/security-audit-export` every minute with `Authorization: Bearer <CRON_SECRET>`. The Vercel cron is declared in `vercel.json`; verify plan/scheduler support. Keep `CRON_SECRET` separate from all authentication/media/export keys. The worker sends up to 100 events per invocation, retries failed records and leases concurrent work. Size scheduling/worker capacity to peak volume; alert on unexported age/queue growth, failed exports, incomplete downloads and `PREVIEW_HARVEST_ALERT`. The staff Security panel exposes harvesting alerts for investigation; external notification routing is an operational monitoring task.
8. Default retention is 365 days with TTL indexes on security events and delivery records. Verify indexes exist, independently protected export retention also expires after 365 days, and documented exceptions have a separate policy. TTL deletion is asynchronous. Compare local/export event counts and investigate unmatched `DOWNLOAD_AUTHORIZED` events rather than treating missing outcomes as successful transfers.

## Session migration and operational behavior

Legacy browser JWTs and printer bearer file URLs are retired. All users must sign in again; preserve uploads, orders and historical audit records. The frontend removes legacy stored tokens and uses a noncredential `cookie` marker in memory. Opaque sessions are stored hashed server-side; browser cookies are Secure/HttpOnly/Strict in production. Staff sessions expire after 30 minutes idle/12 hours absolute; client sessions 30 minutes/eight hours. Current role, activity, token version, authentication contacts and resource assignment are checked on access. Printer sessions last ten minutes and bind to one invitation/file; invitations last 24 hours.

Admin/manager original downloads and sensitive identity/privilege changes require OTP verification within ten minutes. Codes expire after five minutes, allow five attempts, and have shared account/IP sending and verification limits. Resend has a 60-second minimum and invalidates the preceding challenge. Contact replacement requires recent existing-identity verification plus a code at the new destination, then invalidates sessions.

Printer links contain no file capability without SMS verification. Reissue/revoke, changed recipient, cancelled workflow, replaced print file or expired invitation/session invalidates access. Hash checking also detects changed storage bytes. Downloads are streamed from a hashed snapshot through the same audited service used by staff. Transfer completion means the server finished streaming; it cannot prove a person saved, read or did not copy the file.

Clients retain access to the current released version during internal review of a new draft. Releasing a replacement prevents subsequent requests for previous client versions. Already displayed pixels cannot be remotely erased. Text geometry is restricted to current authorized review; watermarks are burned into every page and include viewer/order/version/time/server session reference. Recipients can still capture watermarked pages or photographs.

## Release verification and rollback

Before production activation, verify real HTTPS cookie/CSRF behavior, origin rejection, both OTP providers, storage ACLs, protected audit receiver permissions and export recovery. Check audit visibility is staff-only. Test one authorized download with a synthetic release-test magazine and match its hash/events, then verify revoked sessions and old printer URLs fail.

Do not roll back to a revision accepting arbitrary upload headers, generic media JWTs, public print PDFs or legacy printer capabilities. Prefer a maintenance window or disable downloads while retaining the new authorization middleware. Preserve audit events and uploaded files; do not run destructive migrations. Reverting cookie authentication requires a separate reviewed migration, not restoration of exposed legacy access paths.
